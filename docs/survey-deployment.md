# Размещение отдельной формы опроса

Версия 0.4.0 поставляет две HTML-точки входа. `index.html` открывает учебную платформу с подтверждённым email. `survey.html` открывает анкету через самостоятельный транспорт без account Auth SDK. Реальный сбор в анкете включается только на настроенном отдельном origin.

## Публичная конфигурация

На обоих адресах разместите одинаковый `workshop-config.json`. Образец с вымышленными адресами:

```json
{
  "schemaVersion": 1,
  "supabaseUrl": "https://PROJECT.supabase.co",
  "supabasePublishableKey": "sb_publishable_REPLACE_WITH_PROJECT_PUBLIC_KEY",
  "realtime": true,
  "surveyUrl": "https://survey.example.org/workshop/survey.html",
  "classroomOrigin": "https://class.example.org"
}
```

`supabaseUrl` содержит origin API без пути. `classroomOrigin` содержит origin учебного сайта без пути. `surveyUrl` может включать подкаталог, но должен завершаться `/survey.html`. Запрещены встроенные пароли, параметры query и hash. Адреса учебного сайта и анкеты должны иметь разные origin. HTTP разрешён только для loopback-проверки; реальные телефоны аудитории требуют доступного HTTPS-адреса.

Неверная конфигурация анкеты выключает сбор ответов, сохраняя возможность работы основного учебного приложения. Автономный сервер дополнительно проверяет публичную конфигурацию до старта. `service_role`, `sb_secret_…` и строка подключения PostgreSQL не допускаются в клиент, ZIP и HTML.

Для Vite-разработки аналогичные поля задаются через `VITE_WORKSHOP_SURVEY_URL` и `VITE_WORKSHOP_CLASSROOM_ORIGIN`; адрес и ключ API — через ранее существовавшие `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`.

## Два локальных адреса

После настройки публичного API и миграций можно открыть два терминала в распакованном комплекте. В первом запустите `node scripts/serve.mjs`, во втором — команду с другим портом:

```sh
PORT=4174 node scripts/serve.mjs
```

Настройки для такого прогона: `classroomOrigin=http://127.0.0.1:4173`, `surveyUrl=http://127.0.0.1:4174/survey.html`. На `4173/survey.html` приложение отвергнет сбор личных ответов. На `4174/survey.html` анкета открывается только по приглашению с идентификатором опроса, либо по адресу восстановления из квитанции. Этот запуск использует стандартную библиотеку Node.js и готовые файлы, поэтому не требует установки зависимостей.

Для проверки без реального Supabase существует изолированный тестовый gateway и `playwright.stage-four.config.ts`. Они создают вымышленные аккаунты, используют локальный PostgreSQL и не отправляют писем. Gateway и административный тестовый секрет не публикуются в веб-сборке.

## Статический хостинг

В учебный контур публикуются `index.html`, `assets`, значок, `workshop-config.json` и `data`. В отдельный контур анкеты достаточно опубликовать `survey.html`, используемые им assets, значок и конфигурацию. Корпус программ и учебный HTML анкете не нужны. Корневой адрес публичного контура лучше перенаправить на `survey.html`; страницу учебного входа на этом адресе не размещать.

После `npm run build` данные уже находятся в `dist/data`. Накопительный ZIP исключает второй экземпляр корпуса: для обычного хостинга используйте `public/data`; автономный сервер делает fallback сам.

Для обоих контуров задайте HTTPS, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, ограничивающий Content Security Policy и отсутствие сторонней аналитики/скриптов. Для анкеты не требуется iframe в учебной странице. Ссылка открывается с `noopener noreferrer`. Общий токен приглашения хранится в fragment URL и не передаётся как query веб-серверу; в JSON тела публичного RPC он необходим для проверки приглашения. Личный ключ ответа не помещается ни в какой URL.

RPC-запросы публичной формы содержат только publishable key и JSON; `credentials: omit` исключает cookies, `referrerPolicy: no-referrer` исключает Referrer. Сервер дополнительно отвергает пользовательский JWT. CORS-поведение выбранного API и reverse proxy проверяется при размещении. Точный whitelist в локальном gateway относится к испытанию; настройку CORS реального Supabase этот gateway не изменяет.

## Обновление базы

Поверх зарегистрированных миграций версии 0.3 примените `20261108220024_stage4_barriers_evidence_surveys.sql`. На чистой базе применяются все три миграции в порядке временных меток. Старые файлы этапов 2 и 3 не редактируются. Схемы `private` и `research` должны оставаться закрытыми для прямого PostgREST; анонимные sign-ins Supabase Auth для анкеты не нужны.

Таблицы исследовательской схемы физически находятся в том же проекте БД. Если процедура исследования требует независимого администратора, отдельного региона хранения или иной границы данных, требуется следующий инфраструктурный этап с самостоятельным проектом/API. Текущий релиз не заявляет выполнение требований неизвестного ещё контура размещения.

## Приёмка перед занятием

Проверьте вход по настоящему email, отправку анкеты из чистого браузера на отдельном адресе, скачивание квитанции, восстановление по ней после замены приглашения и отзыв после закрытия. Убедитесь, что в Network формы нет вызовов Auth и пользовательского Authorization, а в проекторном ответе отсутствуют raw answers, account ID и секреты. Проверьте выбранные телефоны, доступность сети зала, Realtime, политику журналов и удаление по сроку. Локальные автоматические проверки входят в комплект; эти эксплуатационные свойства зависят от реального размещения.

Проверка графа собранной анонимной страницы доступна командой `npm run check:survey-bundle`. Она проходит зависимости HTML/JavaScript и отвергает попадание account-модулей или Auth SDK в публичную точку входа. Это дополняет браузерную проверку реальных запросов.
