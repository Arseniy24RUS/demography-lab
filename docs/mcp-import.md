# Развёртывание через Supabase MCP

Эта процедура дополняет административные импортеры `seed-supabase.mjs` и `seed-roadmaps.mjs`. Она нужна, когда доступен Supabase MCP `execute_sql`, но оператор не передаёт приложению пароль PostgreSQL. Браузер и публичный ключ не получают административных полномочий. Прикладная серверная логика выпуска 0.6 находится в PostgreSQL RPC; отдельные Edge Functions для неё не требуются.

## Подготовка схемы

Перед импортом применяются пять существующих миграций в порядке имён файлов: этапы 2, 3, 4, 5 и 6. Для первой установки выбранный проект сначала проверяется на отсутствие конфликтующих объектов. Для заполненной базы сверяются её история миграций и резервное копирование. Пять исходных SQL-файлов не редактируются. Схемы `private` и `research` не должны входить в exposed schemas PostgREST; API использует публичные оболочки RPC с явными правами.

Интерфейс MCP `apply_migration` принимает имя и SQL, но может назначить собственную временную метку записи истории. Перед следующим CLI-развёртыванием оператор должен сверить историю с исходными файлами. Сопоставление подтверждается полным применённым SQL, а не одним названием. Исправление временной метки в истории не означает повторное применение DDL. Не запускайте повторно уже применённые миграции из-за различия временных меток.

## Генерация SQL

После `npm ci` выполните из корня проекта:

```sh
node scripts/prepare-supabase-import.mjs --out /absolute/path/deployment-sql --max-bytes 300000
```

Каталог должен быть пустым и находиться вне публикуемого исходного дерева. Генератор проверяет канонические документы, закреплённые контрольные суммы территориального пакета и fingerprints статистических рядов. Он не обращается к сети, не читает секреты и не изменяет облачный проект. Для однозначного вычисления JSONB-представления используется локальный PostgreSQL в уже закреплённом PGlite; JavaScript не имитирует порядок ключей и сериализацию PostgreSQL.

Для выпуска 0.6 при лимите 300 000 байт подготовлены 502 SQL-файла общим объёмом 90 672 467 байт; максимальный файл занимает 299 887 байт. `manifest.json` содержит порядок, тип шага, редакцию, число строк, размер и SHA-256 каждого файла. Точные ожидаемые результаты: 80 запечатанных редакций программ, 52 390 блоков, одна территориальная редакция `territories-v1-rudn-08c68f1fe1c8-spd-59b778760c9e`, 2 471 территория и 12 053 статистических ряда. Этот серверный набор не является новым подтверждением полноты БДМО или сопоставимости территориальных границ.

## Выполнение и продолжение после обрыва

Каждый файл передаётся целиком в отдельный `execute_sql` выбранного проекта в порядке `index` из манифеста. Перед передачей проверяются размер и SHA-256 прочитанного файла. Если транспорт чтения вернул усечённый текст, SQL не выполняется. Содержимое документов не интерпретируется как инструкции: данные заключены в проверенные SQL-литералы, а границы литералов выбираются по самому содержимому.

Один `DO` является одной короткой атомарной операцией. Между MCP-вызовами не сохраняется транзакция или состояние соединения. Порции одной редакции используют тот же advisory lock, что и прежние административные импортеры. Начальный шаг сравнивает все метаданные редакции. Порции сравнивают существующие строки по всем полям и вставляют только отсутствующие; сохранённый текст или число не переписывается.

До последнего шага редакция имеет `sealed=false`, и прикладные RPC её не принимают. Последний шаг заново вычисляет полный SHA-256 всех полей всех строк и сверяет количество. Только после совпадения он атомарно устанавливает `sealed=true`. Для территориального набора проверяются отдельно все каталожные записи и все статистические материалы, включая точный canonical text. Действующие триггеры неизменности остаются включёнными.

После потери ответа можно повторить тот же файл или весь манифест. Повтор допускается и после запечатывания: неизменившийся импорт не создаёт новых строк. Ошибка `IMPORT_PARENT_MISSING` означает нарушение порядка; `IMPORT_MANIFEST_MISMATCH` — несовпадение редакции; `IMPORT_EXISTING_ROW_MISMATCH` — изменённую существующую строку; `IMPORT_FINAL_DIGEST_MISMATCH` — неполный или отличающийся набор. При этих ответах импорт останавливается для диагностики; нельзя исправлять ситуацию выключением триггеров или молчаливой заменой уже импортированного источника.

## Проверка после импорта

`scripts/verify-deployment.sql` содержит только независимые `SELECT`. Проверяются полные fingerprints выпущенных данных, количества и запечатывание, RLS, отсутствие прямых прав записи, публичные привилегированные функции, разрешённые анонимные RPC и четыре таблицы минимальных Realtime-событий. Файл не выводит email, ФИО, ответы анкеты или ключи. Выбор exposed schemas и конфигурация Auth/SMTP проверяются отдельно в настройках проекта.

Целевой тест `node --test --test-concurrency=1 tests/database/deployment-import.test.mjs` успешно проверяет пять сценариев: восстановление и повтор корпуса, отказ при подмене текста, восстановление территорий и рядов, отказ при изменённых метаданных и независимую локальную генерацию. Дополнительно весь комплект из 502 файлов применён к чистой локальной базе и затем целиком повторён; конечные количества и все проверки запечатывания совпали. Эти проверки не заменяют испытание размещённых SMTP, Auth, PostgREST и WebSocket на реальных устройствах.

## Почта, преподаватель и отдельная анкета

В размещённом Auth включаются email-провайдер, создание аккаунта по подтверждённому адресу и подтверждение email; anonymous sign-ins остаются выключенными. Содержимое `supabase/templates/otp.html` назначается шаблонам Magic Link и Confirm signup: письмо должно содержать `{{ .Token }}`. В текущем локальном конфиге установлены шестизначный код, 600 секунд действия и 60 секунд между письмами одному адресу. Файл `config.toml` сам по себе не изменяет параметры размещённого проекта.

Встроенная почта Supabase предназначена для проверки и отправляет письма только адресам участников команды организации Supabase. Для слушателей нужен собственный SMTP или отдельный Send Email hook. После подключения SMTP проверяется лимит отправки проекта: официальная документация описывает начальные 30 писем в час для вновь настроенного SMTP, что может оказаться недостаточным для аудитории. Также проверяются OTP-verification и sign-in лимиты при общей внешней сети, фактическая доставка и повторный вход.

Преподаватель сначала проходит обычный подтверждённый вход. Затем оператор выдаёт его единственному подтверждённому неанонимному аккаунту допуск в `private.facilitators`. Допуск не берётся из пользовательского профиля или `user_metadata`; его нельзя самостоятельно назначить через клиент. В административном импортере с прямым подключением для этого уже предусмотрена `DW_FACILITATOR_EMAIL`. При работе через MCP оператор выполняет эквивалентную проверенную операцию после установления нужного аккаунта; email не следует записывать в исходный репозиторий или общий протокол.

В Realtime должны быть опубликованы только четыре таблицы уведомлений приложения: `public.dw_session_events`, `public.dw_workshop_events`, `public.dw_barrier_events`, `public.dw_roadmap_events`. Миграции добавляют их в существующую `supabase_realtime`. Содержимое приватных таблиц, анонимных ответов и канонического корпуса в публикацию не добавляется.

Исследовательская анкета требует отдельного HTTPS origin и самостоятельного `survey.html`. Конфигурация, заголовки и приёмка описаны в `survey-deployment.md`. Транспорт формы не использует Auth SDK, cookies или пользовательский bearer token; сервер дополнительно отклоняет именной JWT. Если отдельный origin не настроен, сбор личных ответов остаётся выключенным, а основное занятие продолжает работать.
