# Облачное размещение: проверенное состояние на 9 ноября 2026 года

Проект использует существующий Supabase `demography-lab`, идентификатор `alyrowehwzypgtrqnvdi`, API `https://alyrowehwzypgtrqnvdi.supabase.co`. Новый облачный проект не создавался. Учебное приложение размещается по адресу <https://arseniy24rus.github.io/demography-lab/>, отдельная публичная анкета — <https://demography-lab-survey.sunnydew4.chatgpt.site/survey.html>. Различие origin обеспечивает предусмотренное контрактом разделение учебного интерфейса и анонимной формы.

Облачная установка существенно восстановлена, но **полная готовность совместной мастерской пока не подтверждена**. Осталось одно конкретное подтверждение коннектора Supabase для завершения серверных функций группировки и голосования этапа 3. Автономный режим имеет отдельный локальный сервер и не зависит от этого незавершённого облачного шага.

## Что было обнаружено и восстановлено

Исходная проверка обнаружила в GitHub полный исходный код версии 0.6, однако GitHub Pages публиковал исходный `index.html` со ссылкой на `main.tsx`, вместо результата сборки Vite. Публикация была исправлена отдельным workflow сборки и размещения. Конфигурация приложения использует публичный publishable key; административные ключи в клиентскую сборку не добавлялись.

В Supabase первоначально была применена только миграция этапа 2. Импорт содержал 25 запечатанных редакций документов и одну незавершённую, всего 17 995 блоков. Таблиц последующих этапов не было. Применённый ранее SQL этапа 2 имеет SHA-256 `a70f4eeec6700bfd259a18e922d0a307340709437252a6c22bf19faee326369d`: он точно совпадает с поставляемым историческим файлом, несмотря на отличающийся номер версии в облачной истории.

Все пять исторических SQL-файлов сохранены без изменения. Из-за ограничений и подтверждений коннектора последующие миграции передавались целыми SQL-операторами небольшими частями. На момент проверки в облачной истории находятся **42 записи**, включая дополнительные закрывающие права проверки. Это транспортные части пяти исходных этапов, а не 42 самостоятельных функциональных выпуска. Версии, имена и контрольные суммы принятых сервером SQL сохранены в [машиночитаемом манифесте](../scripts/deploy/cloud-migration-manifest.json).

## Незавершённое подтверждение этапа 3

Коннектор запросил собственное подтверждение для `CREATE FUNCTION`, внутри тела которого присутствует будущая операция `DELETE`. Само определение функции строки не удаляет и функцию не вызывает. Однако подтверждение истекло; коннектор вернул: `This confirmation expired after 2 minutes. Call apply_migration again to get a new confirmation.` Перенос DDL в другой канал, скрытие SQL и обход этого требования не выполнялись.

Готова одна атомарная транзакция [pending-stage3-completion.sql](../scripts/deploy/pending-stage3-completion.sql), размер 15 006 байт, SHA-256 `92bface76daefecdecf8624ccd4f8bc9a5f1f2616f59c0d39e62b6febfb1ca7e`. Она содержит неизменённые определения двух функций, немедленный отзыв унаследованных прав `PUBLIC` и `anon`, оставшиеся публичные оболочки и точное восстановление четырёх ранее разрешённых функций анкеты. Завершающие проверки привилегий откатывают всю транзакцию при нарушении ожидаемых ограничений.

В PGlite была заново воспроизведена частично установленная облачная схема, затем применена именно эта транзакция. Она завершилась успешно; у `anon` нет права исполнения функций группировки, у `authenticated` необходимые права есть. [Результат локальной проверки](../scripts/deploy/pending-stage3-validation.json) отдельно фиксирует `cloudApplied: false`: успешная локальная проверка не означает, что ожидающая подтверждения транзакция уже принята Supabase.

| Оставшаяся группа | Имена функций |
| --- | --- |
| Приватные обработчики группировки | `private.dw_save_family`, `private.dw_delete_family` |
| Публичные назначения и группировка | `public.dw_region_work`, `public.dw_save_family`, `public.dw_delete_family` |
| Публичное управление раундами | `public.dw_open_voting_round`, `public.dw_close_voting_round` |
| Публичная подача голосов | `public.dw_cast_vote`, `public.dw_cast_vote_updates` |
| Компактные обновления мастерской | `public.dw_workshop_updates`, `public.dw_workshop_projector_updates` |

В текущем контуре обнаружены 193 из 204 ожидаемых имён прикладных функций. Действия через оставшиеся RPC пока недоступны. В Realtime включены `dw_session_events`, `dw_barrier_events`, `dw_roadmap_events`; добавление `dw_workshop_events` входит в ожидающую транзакцию. После её подтверждения необходима повторная проверка функций, прав и четырёх таблиц уведомлений.

## Проверка границ доступа

Промежуточное состояние установки дополнительно закрыто: унаследованные права `PUBLIC` на приватные функции отозваны; четыре уже существующих публичных метода чтения мастерской имеют только предусмотренный доступ подтверждённых участников. Проверки из `scripts/verify-deployment.sql` не нашли прикладных таблиц без RLS, прямых утечек прав чтения или записи, публичных `SECURITY DEFINER`-функций, незакреплённого `search_path`, прав исполнения от `PUBLIC` и приватных либо исследовательских таблиц в Realtime.

Для `anon` доступны ровно четыре публичных и четыре соответствующих приватных обработчика анкеты: manifest, чтение собственного ответа, сохранение и отзыв. Автоматическая проверка первоначально отклонила общий `USAGE` для схемы `private`. Вместо повторения той же операции сначала были отозваны лишние права и проверены фактические ограничения. Публичная `SECURITY INVOKER`-оболочка без `USAGE` возвращала `42501: permission denied for schema private`; остальные приватные функции и таблицы были закрыты. Затем коннектор разрешил [отдельную миграцию с SQL-предусловиями](../scripts/deploy/guarded-survey-schema-usage.sql), которая не допускает выдачу `USAGE`, если список функций, RLS, запрет прямых прав на таблицы или guard анонимного запроса изменились. Новые права на таблицы или `CREATE` эта миграция не выдаёт.

Реальные запросы PostgREST с `Content-Profile: private` и `Content-Profile: research` возвращают `406 / PGRST106`: обе схемы не экспонированы через API. Публичный вызов manifest с заведомо неверным приглашением возвращает `400 / SURVEY_INVITATION_INVALID`. Проверка профиля выполняется через конкретный RPC, поскольку корневой OpenAPI endpoint `/rest/v1/` в текущем размещении требует secret key и не подходит для этой проверки с публичным ключом.

## Проверки работающего API и Advisors

В 10:14 UTC скрипт `node scripts/check-deployment.mjs --timeout-ms 10000` завершил **10 из 10 реальных HTTP-проверок**. Подтверждены корректная публичная конфигурация с разными origin, включённый email-провайдер, обязательное подтверждение email, отключённый анонимный Auth, возможность регистрации новых участников, пять запретов чтения учебных данных без входа, закрытость двух схем и отказ по неверному приглашению анкеты. Этот набор проверяет границы публичного доступа; он не проверяет отсутствующие пока операции мастерской или доставку писем.

Security Advisors не вернул предупреждений уровней WARN или ERROR. Информационные сообщения о RLS без политик относятся к 39 намеренно закрытым таблицам в `private` и `research`: доступ к ним реализован проверяемыми RPC, поэтому добавлять разрешающие политики ради исчезновения этого сообщения нельзя. Performance Advisors отметил 10 внешних ключей без полного покрывающего индекса и 31 ещё неиспользованный индекс. Индексы не удалялись: учебных сессий в облаке пока нет. Health Advisors не вернул замечаний. Справочные описания доступны у Supabase: [RLS без политик](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy), [индексы внешних ключей](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys), [неиспользованные индексы](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index).

## Что проверяется перед первым онлайн-занятием

Следующим облачным действием является подтверждение подготовленной транзакции этапа 3. После этого требуется подтверждённый вход преподавателя и явное назначение его конкретной учётной записи в `private.facilitators`. Адрес преподавателя не предполагался по имени и роль произвольному первому зарегистрированному пользователю не выдавалась. Существующий операторский импортёр поддерживает назначение уже подтверждённого аккаунта по явно заданному `DW_FACILITATOR_EMAIL`.

Инструменты коннектора не предоставляют чтение и изменение настроек SMTP, Site URL, redirect allowlist и шаблонов писем. Поэтому эти параметры не объявляются проверенными. Для входа кодом шаблон Magic Link должен содержать `{{ .Token }}`; Site URL и допустимые перенаправления должны соответствовать размещению приложения. По [официальной документации passwordless email](https://supabase.com/docs/guides/auth/auth-email-passwordless) вызов `signInWithOtp` сам по себе не меняет стандартный шаблон ссылки на шаблон кода.

Для массового входа аудитории необходимо проверить собственный SMTP и лимит отправки. [Документация Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp) указывает, что стандартный отправитель ограничен адресами участников команды проекта и не предназначен для рабочего занятия. Доставка настоящих писем, вход преподавателя, работа нескольких подтверждённых аккаунтов и облачный WebSocket Realtime требуют эксплуатационной репетиции; положительный локальный тест и десять публичных HTTP-проверок их не заменяют.

Перед дальнейшим `supabase db push` нужно сверить облачную историю частей с манифестом и с точными историческими исходниками. Нельзя механически помечать все пять миграций выполненными или заново запускать создание уже существующих таблиц. До подтверждения оставшейся транзакции статус установки сохраняется как `partial-stage3-confirmation-required`.
