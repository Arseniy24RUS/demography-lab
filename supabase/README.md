# Выпуск 0.5: дорожные карты

Четвёртая последовательная миграция `20261108225303_stage5_territorial_roadmaps.sql` добавляет территориальные комнаты, совместные записи, проверенные факты реестра, закреплённые основания, версии, рецензии и отдельную проекцию для аудитории. Старые миграции сохраняются без изменений. Порядок административного импорта `scripts/seed-roadmaps.mjs`, проверки редакции данных, команды подключения, RPC и ограничения описаны в [серверном контракте этапа 5](../docs/stage-05-database.md).

Сначала проверьте комплект командой `npm run seed:roadmaps:check`. Импорт в выбранную рабочую базу требует административного соединения и не выполняется из браузера. Отсутствие этого импорта не заменяется фиктивными муниципалитетами или локальными комнатами. Открытый просмотр карт работает из статических данных независимо от подключения общего занятия.

Актуальный итог проверки содержится в [приёмке этапа 5](../docs/stage-05-acceptance.md); дальнейшие разделы сохраняют порядок первичного развёртывания и историю предыдущих модулей. Размещённые Auth, SMTP, PostgREST и Realtime проверяются отдельно для выбранного проекта.

# Сервер учебных сессий и коллективной мастерской — выпуск 0.4

Накопительный выпуск сохраняет этапы 2–3 и добавляет жизненные барьеры, связи с неизменяемыми основаниями, авторские решения и отдельную исследовательскую схему этапа 4. Рабочая облачная среда к комплекту не подключена. Ниже приведены порядок применения миграций, правила доступа, протоколы клиента и фактические границы проверок.

Миграция `migrations/20261108131424_stage2_collaborative_sessions.sql` реализует серверную часть общего занятия: подтверждённую учётную запись, ФИО, сессию, членство, роли, код приглашения, общую доску практик, управление этапом и отдельную проекцию для преподавателя. Она не создаёт аккаунты Auth и не отправляет письма: этим занимается Supabase Auth. Канонический корпус импортируется отдельным административным скриптом из уже включённых в проект данных.

Миграция `migrations/20261108172311_stage3_regions_families_voting.sql` добавляет состояния совместной мастерской, временные назначения регионов, журнал группировки, неизменяемые материалы раундов, допуск к голосованию, закрытые бюллетени и отдельные минимальные уведомления. Проверка источников и прежние RPC сохраняются.

Миграция `migrations/20261108220024_stage4_barriers_evidence_surveys.sql` добавляет именные барьеры и решения, immutable evidence, собственный курсор и отдельно защищённые функции анкеты. [Контракт этапа 4](../packages/barriers/CONTRACT.md), [архитектура](../docs/architecture-stage-04.md), [размещение формы](../docs/survey-deployment.md) и [retention-процедура](../docs/stage-04-database.md) определяют новые границы.

Пароль БД, SMTP и административный ключ отсутствуют в клиенте и в архиве. `config.toml` создан CLI 3.0.0 и настроен для локального Supabase; перенос в иной контур требует его собственных URL, почты и параметров доступа. Принятый на этапе 2 подтверждённый вход по email действует и в версии 0.4. Anonymous Auth здесь не предоставляет доступ к учебным данным. Роль преподавателя выдаётся отдельно на сервере.

| Порядок | Файл | Действие |

Чистая установка применяет три файла в порядке временных меток. При обновлении с версии 0.3 требуется только миграция этапа 4; существующие раунды и бюллетени сохраняются. Для установки версии 0.2, в которой первая миграция уже зарегистрирована, последовательно применяются миграции этапов 3 и 4. Существующие Auth-аккаунты, ФИО, членство, публикации, запечатанные источники и курсоры этапа 2 сохраняются. Именно при переходе 0.2 → 0.3 каждая прежняя сессия получает собственные `boardRevision=0` и курсор мастерской `0`; семейства, назначения и раунды начинают самостоятельную историю. При переходе 0.3 → 0.4 эта история не сбрасывается. Само наличие прежних публикаций не отмечает регион как завершённый.

Обновление 0.3 → 0.4 проверяет сохранность источников, публикаций, членства, курсоров, открытого слепого раунда и нейтрального голоса. Предыдущая регрессия 0.2 → 0.3 также сохранена: два ранее созданных занятия, действующее членство и реальная публикация проходят миграцию, старый snapshot и курсор сохраняются, прежний RPC публикации продолжает работать. Изменение публикации после обновления увеличивает все относящиеся к ней курсоры: занятия, мастерской и барьеров. Администратор конкретного размещения сверяет историю миграций и резервную копию до применения обновления.

## Локальная подготовка

До запуска сервера можно проверить все 80 неизменяемых редакций и выполнить SQL-тесты:

```sh
npm ci
node scripts/seed-supabase.mjs --check
node --test tests/database/*.test.mjs
```

Для полноценного локального стека требуется Docker. CLI 3.0.0 выбирает локальную базу по умолчанию; адрес удалённого проекта необходимо указывать явно. В данном выпуске три миграции проверены на PostgreSQL в PGlite; полный Auth/PostgREST/Realtime стек в среде сборки не был запущен.

```sh
npx supabase start
npx supabase migration up
npx supabase migration list
npx supabase db advisors --type all --level warn --fail-on error
```

Команды не содержат `--remote`. Для существующего размещения оператор сначала сверяет цель, резервное копирование и версию миграций, затем применяет SQL штатным процессом развёртывания выбранного Supabase. В `api.schemas` должны находиться только публичные схемы API. **Схемы `private` и `research` нельзя добавлять в exposed schemas PostgREST.** Public RPC являются `SECURITY INVOKER`; повышение привилегий выполняют только закрытые функции с проверками текущего аккаунта, членства и роли.

Публичные переменные клиента указаны в корневом `.env.example`. Они содержат только URL API и publishable key. `SUPABASE_DB_URL` относится исключительно к административному Node-процессу. Устанавливайте его через окружение/секрет-хранилище сервера; не помещайте строку соединения в `VITE_*`, исходники, опубликованный ZIP или адрес страницы.

## Импорт корпуса и допуск преподавателя

`node scripts/seed-supabase.mjs --check` проверяет структуру, NFC, LF, индивидуальные хеши блоков, согласованность страниц и идентификаторов, полную контрольную сумму представления `layout-canonical-v2`. Это проверка уже включённого канонического текста и сохранённых реквизитов; повторная загрузка и проверка исходных PDF этим скриптом не выполняется.

Для загрузки в выбранную базу выполните скрипт в окружении, где настроен `SUPABASE_DB_URL`:

```sh
node scripts/seed-supabase.mjs
```

При необходимости можно импортировать одну редакцию для локального пилота:

```sh
node scripts/seed-supabase.mjs --document regional-respublika-mordoviia
```

Скрипт использует параметризованные запросы `pg`, порции по 100 блоков и отдельную транзакцию на редакцию. Он сравнивает существующую редакцию с манифестом, не перезаписывает её и позволяет повторить прерванный импорт. После регистрации всех блоков редакция запечатывается. Триггеры запрещают последующее изменение метаданных, текста и порядка, удаление и добавление блоков. Исправленное извлечение должно получить новый идентификатор редакции. Корпус хранится в `private.source_versions` / `private.source_blocks` и не выдаётся через Data API. Второй экземпляр всего корпуса в SQL-миграцию не включён.

Сначала преподаватель выполняет обычный подтверждённый вход по email. Затем оператор задаёт `DW_FACILITATOR_EMAIL` для того же административного процесса и повторяет импорт: уже записанные редакции будут пропущены, а ровно одному найденному подтверждённому, неанонимному аккаунту будет выдан допуск в `private.facilitators`. При неоднозначности адреса или отсутствии подтверждённого аккаунта допуск не выдаётся. Скрипт не создаёт пользователей, не отправляет приглашения и не назначает роль из произвольного клиентского профиля. После выдачи допуска переменную можно удалить из окружения.

Право `canCreateSession` означает возможность создавать сессии. Создатель становится их `host`. Удаление допуска из списка преподавателей запрещает создание новых сессий, но не отбирает права владельца уже созданной сессии: это два разных полномочия. При отзыве допуска оператор устанавливает `revoked_at` в `private.facilitators` штатным административным SQL; пользовательские RPC не имеют права менять эту таблицу.

## Подтверждение email и шаблон OTP

В `config.toml` включены email-провайдер и подтверждение адреса, выключены anonymous sign-ins. Шестизначный OTP действует 600 секунд; повторное письмо одному адресу ограничено интервалом 60 секунд. Шаблон `templates/otp.html` назначен одновременно для `magic_link` и `confirmation`, поскольку первое создание аккаунта и последующий вход могут использовать разные шаблоны Auth. Шаблон выводит `{{ .Token }}`, не требует перехода по ссылке и не загружает внешние ресурсы.

Локальные значения `email_sent`, `sign_in_sign_ups`, `token_verifications` равны 120 для репетиции аудитории за общим NAT. Это настройки локальной конфигурации, а не испытанная пропускная способность размещённого сервиса. Для реального занятия необходимо подключить почтовый транспорт выбранного контура и проверить массовый вход, доставку, повторный код, лимиты провайдера и поведение на общей сети. Встроенная локальная почта и тестовый HTTP gateway не подтверждают доставляемость реальных писем.

## Предметная модель и приватность

| Таблица | Назначение | Доступ участника |
|---|---|---|
| `public.dw_profiles` | ФИО и ревизия; email здесь отсутствует | Собственная запись и имена действующих участников общих сессий; запись только через RPC |
| `public.dw_sessions` | Уровень, регион, этап, статус, ревизия управления, настройка показа | Чтение только текущим членом |
| `public.dw_memberships` | `host / participant / observer`, ревизия членства и отзыв | Действующие участники своей сессии; прямые изменения запрещены |
| `public.dw_submissions` | Один пакет карточки, точных цитат и источников; автор и ревизия | `shared` своей сессии; `withdrawn` только автору и host |
| `public.dw_session_events` | Компактное долговечное уведомление с курсором | Только текущим членам соответствующей сессии |
| `private.invitations` | 12-значный случайный hex-код | Только отдельный host RPC; кода нет в обычном snapshot |
| `private.facilitators` | Предварительно разрешённые создатели сессий | Прямого доступа нет |
| `private.source_versions`, `private.source_blocks` | Запечатанная серверная редакция корпуса | Прямого доступа нет |
| `private.command_receipts` | UUID операции, hash запроса и компактный результат | Прямого доступа нет |
| `private.audit_events` | Автор, тип операции, сущность, ревизия и время | Прямого доступа нет; содержимое цитат, email и коды сюда не пишутся |
| `private.join_attempts` | Окно и счётчик попыток кода | Прямого доступа нет |

Все таблицы включают RLS, в том числе private как дополнительный рубеж. Клиентским ролям не выданы `INSERT`, `UPDATE`, `DELETE` на предметные таблицы. Изменения выполняются командами с авторизацией, ревизиями, журналом и идемпотентностью. Даже прямой вызов private-реализации через SQL-подключение authenticated не позволяет обойти проверки; через REST private-функции вообще не должны быть выставлены.

`auth.uid()` сверяется с существующей записью `auth.users`: нужен подтверждённый email и `is_anonymous=false`. Роли не читаются из `user_metadata`. Отзыв членства проверяется на каждом RPC и SELECT; действующий JWT сам по себе не сохраняет доступ после отзыва. При публикации роль повторно проверяется после блокировки строки сессии, чтобы конкурентная смена роли не обошла проверку записи. Аккаунт Auth и общедоступное имя отделены от кода приглашения и библиографических источников.

Проектор карточек этапа 2 доступен **только host** через `dw_projector_snapshot`. RPC возвращает отдельный allowlist: состояние показа, количество участников, `shared` карточки, их ревизии и разрешённые имена авторов. Ответ не содержит email, membership/user identifiers, локальных ключей, withdrawn-карточек, кода приглашения и чужих профилей. Если `projectorShowAuthors=false`, `authorName` отсутствует даже в сетевом ответе. Проекция мастерской этапа 3 имеет собственные RPC, описанные ниже. Оба режима требуют авторизованного преподавателя; отдельный короткоживущий capability-токен для автономного устройства проектора из полного ТЗ ещё не реализован.

## RPC и ревизии

Имена параметров точны; клиентский wire-контракт находится в `packages/collaboration/types.ts`, проверка DTO — в `schema.ts`. Автор определяется сервером. Большинство изменяющих команд возвращают актуальный `SessionSnapshot`; профиль возвращает `SessionProfile`. Внутренние SQL-колонки используют snake_case, JSON API — camelCase.

| Public RPC | Параметры | Результат и допуск |
|---|---|---|
| `dw_bootstrap` | Нет | `{profile, canCreateSession, sessions}`; отсутствие первого профиля допустимо |
| `dw_save_profile` | `p_operation_id`, `p_expected_revision`, `p_full_name` | Profile; создание с revision `0`, изменение с текущей ревизией |
| `dw_create_session` | `p_operation_id`, `p_title`, `p_scope`, `p_region_id` | Snapshot; только разрешённый facilitator с профилем |
| `dw_join_session` | `p_operation_id`, `p_code` | Snapshot или committed `{error:{code,...}}` |
| `dw_session_snapshot` | `p_session_id` | Согласованный snapshot текущего члена |
| `dw_session_cursor` | `p_session_id` | Скалярный JSON number; текущий член; экономичная проверка изменений |
| `dw_projector_snapshot` | `p_session_id` | ProjectionSession; только host |
| `dw_invitation` | `p_session_id` | `{code, revision}`; только host, revision относится к сессии |
| `dw_rotate_invitation` | `p_operation_id`, `p_session_id`, `p_expected_revision` | Snapshot; host; меняет код и ревизию сессии |
| `dw_update_session` | `p_operation_id`, `p_session_id`, `p_expected_revision`, `p_patch` | Snapshot; host; разрешённые поля: title, status, phase, joinOpen, focusSubmissionId, projectorShowAuthors |
| `dw_publish_submission` | `p_operation_id`, `p_session_id`, `p_local_key`, `p_expected_revision`, `p_bundle` | Snapshot; создание с revision `null`, изменение с ревизией публикации |
| `dw_moderate_submission` | `p_operation_id`, `p_session_id`, `p_submission_id`, `p_expected_revision`, `p_status` | Snapshot; `shared / withdrawn` с ревизией публикации |
| `dw_set_member_role` | `p_operation_id`, `p_session_id`, `p_member_id`, `p_expected_revision`, `p_role` | Snapshot; host; revision членства, `participant / observer`; владельца менять нельзя |
| `dw_revoke_member` | `p_operation_id`, `p_session_id`, `p_member_id`, `p_expected_revision` | Snapshot; host; revision членства; владельца отзывать нельзя |

Для `municipality` и `region` нужен `regionId`. Для `federal` он может отсутствовать. Уровень сессии задаёт учебный контекст и не ограничивает чтение корпуса этим регионом: сравнение мер разных регионов остаётся основным заданием. При этом каждая опубликованная карточка сохраняет свой исходный регион; цитата из программы другого региона не может молча удостоверить её реквизиты. Межрегиональная адаптация как самостоятельное проектное решение относится к последующему модулю.

Одно имя `localKey` уникально внутри `(session, author)`. Присвоить чужое авторство или переписать чужую карточку передачей её ID нельзя. Повторное создание своей карточки с тем же practice ID и новым localKey также запрещено. Host может скрыть карточку, но не переписать чужое содержимое от имени автора.

### Время занятия и права записи

| Действие | Требования к состоянию |
|---|---|
| Публикация и изменение своего bundle | host или participant; `status=open`; `phase=reading` или `review` |
| Отзыв своей карточки участником | Те же открытый статус и этапы; восстановление самостоятельно запрещено |
| Модерация `shared ↔ withdrawn` преподавателем | Любой этап и статус; чужой bundle при этом не меняется |
| Смена этапа, статуса, focus, кода, ролей | Только host; закрытую сессию можно снова открыть |
| Первое присоединение по коду | `joinOpen=true`, статус не `closed`; при `paused` разрешён вход для чтения |
| Чтение и повторный вход действующего члена | Разрешены и после закрытия; отозванный член доступа не получает |
| Восстановление withdrawn | Только host; редактирование withdrawn автором запрещено |

Начиная с версии 0.3 правила публикации и модерации дополнены защитой открытого раунда. Для публикации, включённой в его состав, изменение bundle или статуса отклоняется с `ROUND_OPEN`, в том числе при попытке преподавателя скрыть карточку. Сначала преподаватель закрывает раунд. Прежние ограничения остаются действующими для остальных публикаций.

`expectedRevision` защищает конкретную сущность. Ревизия сессии меняется при настройке занятия и при автоматическом снятии focus со скрытой карточки; обычная публикация другого участника её не увеличивает. Ревизии публикации, профиля и членства самостоятельны. `cursor` увеличивается при предметных изменениях в области сессии, включая ФИО действующего члена. Эти числа нельзя подменять друг другом.

Операция сериализуется по `(auth.uid(), operation UUID)`. Сервер хеширует каноническое JSONB-представление запроса SHA-256 и проверяет его вместе с типом команды. Повтор UUID с другим payload получает `IDEMPOTENCY_CONFLICT`. Повтор успешной команды не создаёт новых записей/ревизий/событий; возвращает актуальный snapshot той же сессии, который может содержать более поздние действия коллег. Receipt хранит компактный идентификатор результата, а не копию всей доски. Это гарантирует один эффект операции и экономит место; побайтовая неизменность повторного snapshot не обещается.

Предметная запись, receipt, закрытый audit и безопасное событие создаются в одной транзакции. Ошибочная цитата, конфликт или отказ доступа не оставляют частично опубликованную карточку. Журнал `dw_session_events` одновременно служит долговечным уведомлением; его события содержат только тип, идентификатор, ревизию и курсор. Потерянное уведомление восстанавливается чтением текущего snapshot.

## Проверка карточки и источника

Сервер требует как минимум одну цитату, одну ссылку на известную редакцию и точное совпадение набора occurrence IDs карточки с массивом её фрагментов. Непредусмотренные поля объектов, неправильные типы, повтор идентификаторов и неизвестные ссылки отклоняются. Источник обязан предъявить полный SHA-256 сохранённого PDF, идентификатор документа, редакцию и нормализацию. Эти реквизиты сверяются с запечатанным реестром. В опубликованном bundle источник заменяется каноническими title, URL, hash и region; произвольная клиентская подпись не становится серверным библиографическим описанием.

Для каждого span проверяются существование блока в нужной редакции, возрастающий порядок блоков, страница в пределах редакции, целочисленные `start/end`, точное `exact`, соседние `prefix/suffix` и их положение. `start` отсчитывается с нуля, `end` не включается. PostgreSQL `char_length`/`substring` используют символы UTF-8: emoji и символы за пределами BMP не превращаются в два UTF-16 индекса. Нормализация уже выполнена при импорте; SQL не сжимает пробелы и не подправляет цитату, чтобы она «совпала».

Проверка поля `verified` требует `reviewedValue`, равный текущему точному текстовому представлению соответствующего поля. Для `conditions` это соединение элементов через LF. Изменение значения требует новой проверки; устаревшая отметка не переносится автоматически. Сервер удостоверяет точность источника и целостность записи проверки пользователя. Он не устанавливает причинную эффективность меры, действительность права на дату занятия или истинность содержательного вывода.

## Лимиты, ошибки и синхронизация

Один bundle ограничен 128 KiB серверного JSONB-представления; допускается до 128 источников и фрагментов, 256 spans на один anchor и 256 записей field evidence. Текстовые пределы согласованы с клиентской схемой: ФИО до 200 символов, название карточки до 500, обоснование `note` до 4000. Серверный лимит с учётом сериализации может сработать чуть раньше клиентского ограничения компактного JSON.

В сессии максимум 1000 действующих членов, 5000 публикаций и 4 MiB суммарных bundle, включая withdrawn. Последний предел ограничивает объём полного snapshot до появления серверной пагинации. Это верхние ограничения реализации, не результаты нагрузочного испытания такого масштаба. Сжатие HTTP на фактическом хостинге следует настраивать отдельно.

`dw_session_cursor` позволяет опрашивать состояние без повторной загрузки всех цитат. При равном курсоре клиент сохраняет текущую доску. После увеличения курсора или уведомления Realtime он получает полный snapshot. Этап 2 использует таблицу `dw_session_events`; этап 3 добавляет независимую `dw_workshop_events`. Миграции включают эти две таблицы в publication `supabase_realtime`, если она уже существует. Для размещения, в котором publication отсутствовала при применении миграций, оператор включает в Realtime только соответствующие таблицы уведомлений после настройки сервиса. Полные тексты, карточки, профили, бюллетени и коды в события не включены. RPC polling восстанавливает актуальное состояние из PostgreSQL при отсутствии или потере уведомления. Одновременное редактирование общего повествовательного документа посредством CRDT относится к следующим модулям.

Код сессии — 12 случайных hex-символов в верхнем регистре, 48 бит энтропии; при вводе разрешены пробелы, дефисы и нижний регистр. За десять минут один подтверждённый аккаунт может выполнить восемь новых попыток. Повтор уже учтённого UUID не расходует попытку повторно. Неверный код и закрытый вход возвращают `{error:{code}}`, чтобы счётчик сохранился после commit. `RATE_LIMITED` также возвращает `retryAfterSeconds`. Обычный SQL `RAISE` откатил бы счётчик, поэтому для этого случая применяется отдельный протокол ошибок.

Остальные предметные отказы имеют SQLSTATE `P0001` и стабильный `message`: `AUTH_REQUIRED`, `EMAIL_NOT_VERIFIED`, `PROFILE_REQUIRED`, `FORBIDDEN`, `INVALID_INPUT`, `REVISION_CONFLICT`, `IDEMPOTENCY_CONFLICT`, `SESSION_NOT_OPEN`, `PHASE_CLOSED`, `SOURCE_MISMATCH`, `CORPUS_NOT_READY`, `LIMIT_EXCEEDED`. Административный запрет изменения источника имеет `SOURCE_IMMUTABLE`. Клиент не должен повторять конфликт как сетевой сбой и не должен показывать «сохранено» без успешного RPC. Отсутствующая или чужая сессия обычно отвечает `FORBIDDEN`, не раскрывая чужие идентификаторы.

## Мастерская этапа 3: модель данных и доступ

Контракт находится в [packages/workshop/CONTRACT.md](../packages/workshop/CONTRACT.md), типы — в [types.ts](../packages/workshop/types.ts), строгая проверка ответов — в [schema.ts](../packages/workshop/schema.ts). Состояние этапа 3 возвращается отдельным `WorkshopSnapshot`. Обычный `SessionSnapshot` сохраняет прежнюю структуру и API.

| Таблица | Назначение | Доступ клиента |

Все десять новых таблиц в `private` и публичная таблица уведомлений имеют RLS. На частные таблицы отсутствуют прямые клиентские права. Публичные функции используют `SECURITY INVOKER`; закрытые реализации проверяют подтверждённый аккаунт и текущее членство, а при записи повторяют проверку после блокировки сессии. Схема `private` остаётся исключённой из PostgREST. Роль `observer` разрешает чтение доступной части мастерской и исключает назначение регионов, редактирование групп и голосование.

Новая таблица событий передаёт только сигнал изменения. Голосование не увеличивает курсор этапа 2 и не заставляет повторно загружать прежнюю общую доску. Изменение публикации, роли, доступа, ФИО или значимых настроек занятия инвалидирует соответствующее состояние мастерской. Текущий доступ проверяется и при чтении скалярного курсора, поэтому ранее выданный токен не сохраняет доступ после отзыва членства в занятии.

### Региональные назначения

Выбор региона выполняется атомарно. Назначить можно регион, для которого на сервере имеется запечатанная редакция корпуса. Первая команда использует ревизию `0`; для существующей записи требуется её текущая ревизия. Соперничающий выбор со старой ревизией получает `REVISION_CONFLICT`, попытка занять действующее чужое назначение — `REGION_TAKEN`. Преподаватель может освободить или переоткрыть назначение и взять его на себя.

`claim`, `reopen` и явный `renew` задают срок на 30 минут. `leaseExpiresAt` возвращается клиенту вместе с ревизией. Истёкшее назначение можно выдать повторно с текущей ревизией. Прежний исполнитель с устаревшей командой не завершает новое назначение. Завершение и продление истёкшей записи отклоняются с `LEASE_EXPIRED`; требуется повторное получение свободного назначения. Срок проверяется серверными часами. Истечение времени само по себе не создаёт событие: интерфейс учитывает возвращённую дату и повторно проверяет право при следующем действии.

Команда `complete` требует действующего назначения и опубликованной карточки с источником того же региона либо пояснения длиной не менее десяти символов после удаления крайних пробелов. Пояснение позволяет зафиксировать отсутствие отобранных практик. Статус отражает заявленное завершение отбора в рамках учебного задания; он не устанавливает прочтение каждой страницы или независимую экспертизу всего документа. В версии 0.3 применяется одно назначение на регион; пакеты разделов и параллельная независимая проверка относятся к следующему развитию.

### Семейства и сохранение исходных вариантов

Преподаватель задаёт название общего механизма, его описание, основание группировки и полный состав публикаций. Сохранение проверяет `boardRevision` и атомарно переносит выбранные публикации из прежних групп. Одна публикация входит не более чем в одно действующее семейство. Опустевшее семейство сохраняется для явного изменения или удаления; сами публикации продолжают существовать.

Регион, получатели, суммы, условия, поля проверки и точные цитаты каждого исходного bundle остаются неизменными при группировке. Автоматическое сходство названий не вызывает серверного слияния. Журнал `dw_family_history` сохраняет группировки до и после изменения. Текущее разделение и перенос выполняются тем же API; отдельное восстановление исторической версии через пользовательский RPC в этом выпуске не предоставлено.

### Зафиксированный раунд и права участия

| Действие | Серверные условия |
|---|---|
| Взять, продлить или завершить регион | host/participant, открытая сессия, этап reading/review, допустимый владелец и ревизия |
| Создать, изменить или удалить семейство | host, открытая сессия, reading/review, отсутствие открытого раунда, текущая `boardRevision` |
| Открыть раунд | host, открытая сессия, discussion, хотя бы одно непустое семейство, текущая `boardRevision` |
| Подать, изменить или снять ответ | Текущий host/participant из зафиксированного списка, открытые сессия и раунд, discussion, ревизия собственного бюллетеня |
| Закрыть раунд | host и текущая ревизия открытого раунда; возможно также при приостановленном или закрытом занятии |
| Читать прежний раунд | Действующее членство в занятии; роль наблюдателя допустима |
| Читать проекцию мастерской | Только host |

Открытие фиксирует все непустые семейства, исходные bundle и ревизии публикаций. `promptText` по умолчанию равен «Считаете ли Вы эту практику приоритетной для адаптации в выбранном контексте?». `contextScope` и `contextRegionId` копируются из занятия; измерение оценки — `priority_for_adaptation`. Вопрос и пороги задаются до начала. Материалы и список допущенных участников запечатываются; триггеры запрещают последующие правки, удаление и добавление новых элементов. Во время открытого раунда блокируются изменение участвующих публикаций и редактирование семейств. После закрытия новая редакция оценивается в самостоятельном раунде; прошлые ответы в него не переносятся.

В допуск входят подтверждённые действующие host и participant на момент открытия, включая преподавателя. Позже присоединившийся слушатель участвует в следующем раунде. Последующее превращение участника в observer или отзыв членства блокирует новые команды, сохраняя уже поданные ответы и исходный знаменатель. Каждому допущенному участнику назначены все семейства. Для каждого записывается случайный seed; порядок его карточек воспроизводится при повторной загрузке. Сбалансированные пакеты назначения оценок пока не реализованы.

Первый раунд требует `resultsVisibility=after_close`: запрос первого открытого показа отклоняется с `FIRST_ROUND_BLIND`. До закрытия сервер возвращает `totals:null` для каждого семейства всем ролям и проектору; доступно лишь общее число участников, подавших хотя бы один ответ. Последующий раунд может использовать явно выбранный преподавателем режим `live`. Закрытие раскрывает агрегаты и завершает изменение бюллетеней.

### Ответы, знаменатели и рейтинг

`+1` означает поддержку, `-1` — отсутствие поддержки в заданном контексте, `0` — ответ «не могу оценить». `null` означает отсутствие или снятие ответа. Снятие сохраняет запись с новой ревизией, позволяя обнаруживать конфликт между устройствами. Сервер возвращает только собственные `myVote` и `myVoteRevision`; чужие бюллетени отсутствуют в DTO. Физическое удаление бюллетеня и изменение его после закрытия блокируются также триггером. Привязка ответа к аккаунту служит проверке допуска и единственности ответа.

Для каждого семейства сохраняются A — поддержка, D — отсутствие поддержки, Z — «не могу оценить», R — допущено. API возвращает `substantive=A+D`, `cast=A+D+Z`, `unanswered=R-cast`, `coverage=cast/R`, `supportRatio=A/(A+D)`, `net=(A-D)/(A+D)` и дополнительную разность `score=A-D`. При нулевом знаменателе соответствующая доля равна JSON null. Рейтинг использует net после проверки охвата и содержательных ответов; простая разность score не заменяет долю.

По умолчанию `minCoverage=0.7`, `minSubstantiveVotes=min(3,R)`. Преподаватель может изменить пороги перед открытием: охват от 0 до 1, минимальное число содержательных ответов — целое от 1 до R. Признак `qualifies` требует выполнения обоих порогов. Клиентская схема повторно проверяет доли по исходным числителям и знаменателям. Подпись результата — «Оценка участников сессии»; причинный эффект меры на рождаемость из голосования не рассчитывается.

Точные именованные параметры приведены в [контракте RPC](../packages/workshop/CONTRACT.md). Все команды записи требуют UUID операции и используют прежний протокол идемпотентности. Полные RPC сохранены для совместимости и восстановления кэша.

Компактный запрос передаёт `p_known_round_id` только при наличии полного проверенного материала того же аккаунта, занятия и раунда. Если идентификатор совпадает с последним раундом, сервер заменяет только `round.families[].variants` на null. Ответы пользователя, агрегаты, права, сроки и курсоры остаются актуальными. Клиент восстанавливает варианты по их семействам и затем выполняет строгую проверку всего DTO. Отсутствующий кэш требует полного запроса с `p_known_round_id:null`. При новом или неизвестном раунде сервер сразу возвращает полные материалы. Подстановка пустого массива или цитаты другого семейства недопустима.

Параметр `p_known_round_id` определяет форму ответа и исключён из идентичности команды: повтор голосования после потери кэша не создаёт второй эффект. Отдельный курсор и компактные ответы уменьшают повторные сетевые загрузки. В тесте двух реальных региональных вариантов компактный JSON занимает менее половины полного ответа. На сервере пока строится ограниченный полный JSON перед исключением материалов; данный механизм не является доказательством масштабирования по CPU.

Проекция этапа 3 не содержит имён и идентификаторов участников, владельцев назначений, их личных бюллетеней, локальных ключей и приглашений. Свободный авторский текст в карточках и пояснениях не проходит автоматическую анонимизацию. Полный и компактный методы проекции требуют текущей роли host.

### Пределы этапа 3 и диагностические ответы

В занятии допускается до 200 семейств и 100 раундов. Один раунд фиксирует до 1000 участников и до 200 непустых семейств. На замороженные bundle установлен предел 8 MiB для раунда и 64 MiB суммарно для занятия; метаданные семейств имеют отдельные текстовые ограничения. Одно название семейства ограничено 300 символами, механизм и основание — по 4000. Прежний предел текущих публикаций 4 MiB сохраняется. Указанные числа ограничивают запросы и накопление состояния; нагрузочное испытание на предельных значениях не проводилось.

Дополнительные предметные коды: `REGION_UNAVAILABLE`, `REGION_TAKEN`, `LEASE_EXPIRED`, `COMPLETION_NOTE_REQUIRED`, `ROUND_OPEN`, `ROUND_CLOSED`, `ROUND_NOT_READY`, `NOT_ELIGIBLE`, `FIRST_ROUND_BLIND`. Защита запечатанного материала также использует `ROUND_IMMUTABLE`. Коды конфликтов, прав доступа, состояния сессии и проверки источников сохраняют значение этапа 2.

## Проверено и что остаётся проверить при размещении

Для выпуска 0.3 полный SQL-набор `node --test tests/database/*.test.mjs` завершился успешно: **45 из 45 проверок**, включая 23 проверки прежнего модуля и 22 проверки мастерской. Сценарии применяют поставляемые SQL-файлы к PostgreSQL 18.6 в PGlite 0.5.15, переключают роль на `authenticated`, задают claims Auth и проверяют положительные и отрицательные исходы. Основные предметные фикстуры используют реальные источники Мордовии и Сахалина. Дополнительная явно синтетическая Unicode-фикстура этапа 2 проверяет emoji, supplementary-plane символы и комбинируемые последовательности; она не включена в опубликованный корпус программ.

Историческая приёмка этапа 2 включала успешные 23 SQL-теста и отдельный полный прогон корпуса: чистая база получила все 80 реальных редакций и 52 390 блоков, запечатала их и повторила импорт всех 80 без изменения реестра. Затем серверный validator принял все 15 подготовленных карточек и 56 их реальных цитат. Полный импорт, повторный импорт и проверка карточек заняли в том однократном прогоне 5016 мс. Протокол сохранён в [validation-result.json](../tests/database/validation-result.json); время этого прогона не является нагрузочным нормативом размещённого сервиса.

SQL-тесты покрывают текущую подтверждённую identity, игнорирование `user_metadata`, RLS и запреты прямых изменений, приватность кода и email, целостность источников, равнодлинную подмену цитаты, повтор операций, устаревшие ревизии, этапы, observer, отзыв членства, withdrawn и серверную проекцию. Дополнительные клиентские и браузерные тесты находятся в `tests/collaboration` и `tests/e2e`.

Новые проверки дополнительно подтверждают конкурирующий выбор региона, истечение и повторную выдачу назначения, запрет завершения старой ревизией, обоснование отсутствия находок, неизменность двух региональных вариантов при группировке, замораживание материалов и списка участников, устойчивый персональный порядок, скрытые итоги первого раунда, различие нуля и отсутствия ответа, формулы и пороги, закрытие, повторные команды, позднее присоединение и приватность проектора. Отдельный сценарий применяет этап 3 к уже заполненной базе этапа 2 и проверяет продолжение работы прежнего API. Проверены полные и компактные ответы, восстановление при неизвестном раунде и неизменность эффекта повторной команды.

Шесть проверок Zod-контракта успешно проверили транспортные границы, запрет утечки скрытых итогов и личных полей на проектор, точность долей по исходным числам, уникальность назначений и обязательное восстановление компактного материала перед разбором. `tsc --noEmit --pretty false` также завершился успешно. Машиночитаемый протокол этапа 3 находится в [stage-three-validation-result.json](../tests/database/stage-three-validation-result.json).

При подготовке этапа 2 команда `supabase db advisors --type security --fail-on error` обращалась к **локальному** адресу 127.0.0.1:54322 и остановилась на `ECONNREFUSED`. В этапе 3 выполнена попытка `supabase db advisors --type all --level warn --fail-on error` с тем же исходом: полный Docker-стек отсутствует. Проверка Advisors в рабочем Supabase-проекте остаётся задачей развёртывания. Облачные проекты и их схема в ходе подготовки этих выпусков не изменялись.

PGlite проверяет фактический SQL и права PostgreSQL на одном соединении; тестовый HTTP gateway проверяет клиентский протокол. Размещённые SMTP, Auth, PostgREST и WebSocket Realtime здесь не испытаны. Несколько одновременных соединений PostgreSQL, массовый вход аудитории, задержки сети и нагрузку нужно проверить в выбранном контуре перед занятием. Положительный локальный протокол не заменяет подтверждение работоспособности подключённой облачной среды.

## Этап 4 и отдельная анкета

Именная доска использует `dw_barrier_events` и свой cursor. Материалы оснований загружаются отдельным RPC; перед повторным чтением кеша подтверждается текущее членство. На каждый анонимный ответ событие не публикуется. Редкая сверка обновляет безопасный aggregate, а raw view остаётся явным host-only действием. Приглашение проверяется через `dw_survey_invitation_state`, не загружая ответы.

Четыре публичных RPC анкеты допускают только anon: manifest, own, save и withdraw. Учебный пользовательский JWT отвергается самим сервером. Общая ссылка не обеспечивает уникальность физического человека. Исследовательская схема физически расположена в том же проекте; независимое хранилище требует отдельного инфраструктурного этапа.

Истечение retention закрывает чтение и экспорт. Для фактической очистки используйте преподавательский purge либо операторский `scripts/purge-expired-surveys.mjs`: dry-run по умолчанию, `--apply` выполняет транзакционную очистку. Квитанции/tombstones сохраняются для защиты от replay; политики backup/log retention выбираются при размещении. [Полная инструкция](../docs/stage-04-database.md) содержит точные команды и ограничения.
